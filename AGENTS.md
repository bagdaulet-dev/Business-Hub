# CollectWatch — инструкции для AI-агентов

## 1. Контекст проекта и начало сессии

- Business-Hub — репозиторий **CollectWatch**: поиск подходящих объявлений eBay, сравнение цен, Watchlist и рекомендации Kimi. Текущие категории — коллекционные карточки и электроника.
- Прочитай [README.md](README.md) и [docs/TECHNICAL.md](docs/TECHNICAL.md). README описывает продукт; технический документ содержит фактическую реализацию, API, проверки и ограничения.
- Текущий набор — сохранённые реальные объявления; появление новых записей разыгрывается локально. Не выдавай его за живой мониторинг eBay. Публичный UI сохраняет пояснение в футере.
- Kimi разбирает запрос и объясняет выбор; код применяет ручные фильтры, сопоставляет товары и считает цены. Не подменяй неизвестные значения вымышленными.
- Риск-скоринг исключён. Не добавляй оценки подлинности, fraud probability или бейджи безопасности.
- Раздел метрик пуст до получения нового исследования команды. Старые рыночные цифры и финансовые прогнозы из истории Git не переносить в актуальные материалы.
- Деплой и автодеплой отложены до отдельной задачи. Секреты остаются в локальном окружении.

## 2. Общие правила работы

- Следуй актуальной задаче пользователя, действуй самостоятельно в разрешённом объёме. Обзор проекта не означает начало разработки или запуск платных интеграций.
- Общайся по-русски, конкретно. Объясняй результат, проверку, ограничения и следующий шаг; подробность подбирай под запрос пользователя.
- Различай предложение, согласованное решение, реализацию и проверенное поведение. Текстовая рецензия не равна проверке продукта пользователями.
- Сохраняй ручные изменения и учитывай уже принятые решения. Не запрашивай повторное согласие на разрешённые действия; уточняй только существенные недостающие данные или новый объём работ.
- Секреты, значения `.env*`, ключи API, `DATABASE_URL`, частные данные и логи с ними не выводи и не коммить. В `.env.example` разрешены только имена переменных и безопасные примеры.

## 3. Делегирование и переиспользование сессий

- Главный агент координирует работу, интегрирует изменения и проверяет итог. Делегируй самостоятельные полезные части, когда это применимо; тривиальные действия выполняй сам.
- Перед созданием субагента проверь доступные существующие сессии. Продолжай подходящую сессию, если её контекст полезен; новую создавай для отдельной задачи или несовместимого контекста. Не обещай переиспользование сессии, недоступной в текущей среде.
- Каждому субагенту задавай ограниченную задачу, необходимые факты, область владения файлами, ограничения и формат результата. Передавай минимально достаточный контекст вместо всей истории без необходимости.
- Разделяй независимые задачи и файлы между агентами. Не запускай двух редакторов одного файла одновременно; общие контракты согласуй до параллельных изменений.
- Не дублируй анализ, уже порученный субагенту. Пока он работает, выполняй другую полезную часть; результат оцени по доказательствам, diff и подходящим проверкам.
- Для существенного пользовательского сценария поручай независимую проверку полноты и удобства. Учитывай суммарный расход всех агентов; не создавай их ради простого ожидания или повторного чтения тех же логов.
- Проси краткую передачу результата: что сделано, какие файлы изменены, что проверено, риски и нерешённые вопросы. Не создавай пользовательские чаты автоматически.

## 4. Эффективность, контекст и расход токенов

- Сначала используй уже полученные факты и результаты. Повторяй чтение при изменении состояния, устаревании данных или конкретном сомнении; перед существенными выводами проверяй актуальный источник.
- Ищи адресно: известная папка → список файлов через `rg --files` → нужный фрагмент через `rg`. Не начинай с обхода всего профиля пользователя и не загружай целиком большие файлы, датасеты или длинные логи.
- Из каталога инструментов выбирай нужные имена и описания; полную схему читай только для выбранного инструмента. Подключай только относящиеся к задаче скиллы.
- Объединяй независимые чтения и проверки; зависимые операции, изменения и решения выполняй последовательно, проверяя ошибки.
- Не опрашивай неизменное состояние часто. Используй ожидание завершения или редкие проверки соразмерно длительности работы; не обещай автоматическое возвращение без действующего механизма.
- Проверяй изменения соразмерно риску. После достаточных успешных проверок завершай задачу; расширяй тестирование при новых изменениях, ошибках или нерешённых сомнениях.
- Не повторяй в ответах уже сказанное без необходимости. Экономь за счёт организации работы, а не пропуска обязательных проверок или запрошенных деталей.

## 5. Длительные вычисления и эксперименты

- Для обучения, оценки моделей и других длительных вычислений агент готовит запуск и анализирует результаты, а повторяющуюся работу выполняют автономные скрипты.
- Сначала проверь данные и сделай короткий пробный запуск. Полный запуск сохраняет конфигурацию, логи, checkpoints (если применимо) и метрики в файлы; проверки и остановку при ошибке выполняй программно.
- Если серия экспериментов не согласована, после пробы запускай один полный эксперимент. Дополнительные полные эксперименты сначала предложи с объяснением цели; рутинные исправления согласованного запуска выполняй самостоятельно.
- Читай сводные метрики, нужные примеры и релевантный фрагмент ошибки. Не выделяй субагентов для ожидания и не обещай точный процент экономии или программное ограничение недельного лимита без подтверждённого механизма.

## 6. Скиллы и общая библиотека

- Репозиторий https://github.com/aibarC/agent-toolkit, локальная копия /Users/srkaibar/agent-toolkit.
- При первом обращении к библиотеке в новой сессии перед показом каталога, подбором, установкой или изменением скиллов проверь origin. Он должен вести именно на github.com/aibarC/agent-toolkit по HTTPS или SSH. При несовпадении останови обновление.
- Проверь рабочее дерево и успешно выполни git fetch origin refs/heads/main:refs/remotes/origin/main. Сравни HEAD со свежим ref.
- Автоматически обновляй только чистую main командой git merge --ff-only refs/remotes/origin/main. После fast-forward проверь чистоту дерева и равенство HEAD и origin/main. Только тогда называй копию актуальной на момент fetch.
- При грязном дереве, другой ветке, локальных коммитах или расхождении ничего не перезаписывай и сообщи состояние. Ошибка fetch или отсутствие сети означает, что актуальность не проверена.
- Затем прочитай README.md и CATALOG.md библиотеки. Зафиксируй используемый SHA на время задачи. Перед публикацией повтори проверку GitHub. Полная синхронизация на каждой правке с уже выбранным скиллом не нужна.
- Проверяй фактические глобальные и проектные папки, цели ссылок и доступность текущему агенту. Каталог не является реестром установок.
- Сначала ищи в общей библиотеке. Новое добавляй с источником и лицензией в запрошенную область установки.
- Указание библиотеки не доказывает установку скиллов в этом проекте. Не устанавливай и не синхронизируй их без относящейся к задаче необходимости; на другой машине сначала проверь доступность указанного локального пути.

## 7. Git, совместная работа и завершение

- Ожидаемый origin — `https://github.com/bagdaulet-dev/Business-Hub.git` либо SSH-эквивалент. Перед изменениями проверь рабочее дерево, ветку и origin; перед синхронизацией и push получи свежие сведения о целевой удалённой ветке.
- Разработка: `aibarC` владеет веткой `work/data-engine`, `bagdaulet-dev` — `work/app`. Создавай их от свежего main при начале реализации. Один владелец на ветку; публикуй свою ветку и PR в main. Прежнее общее разрешение прямого push в main отменено. Интегратор — bagdaulet-dev: последовательно проверяет и объединяет PR. На чистой main обновляйся только fast-forward.
- Опубликованные рабочие ветки обновляй обычным merge свежего origin/main, без rebase/force push. Дополнительным субагентам назначай независимые файлы и при необходимости отдельные checkout/дочерние ветки.
- Текущее разовое исключение: пользователь разрешил объединить актуальные ветки CollectWatch в main и очистить документацию. Это не меняет обычное разделение рабочих веток для дальнейшей разработки.
- Не применяй force push, `reset --hard`, `git clean` и не уничтожай чужие незакоммиченные изменения. При отклонённом push сначала fetch и разбор расхождения; не выбирай целиком одну сторону конфликта без чтения обеих.
- `aibarC`: `src/engine/`, `src/providers/`, `data/demo/`, `tests/engine/` — данные, AI, сопоставление и расчёт. `bagdaulet-dev`: `src/app/`, `src/components/`, `src/server/`, `tests/integration/` — приложение, HTTP API, хранение и деплой. Фактические клиентские точки входа также находятся в корне: app.mjs, watch-ui.mjs, recommendation-ui.mjs, index.html и style.css.
- `bagdaulet-dev` владеет `src/contracts/`, зависимостями/lock-файлами, конфигурацией, миграциями, CI и общими документами. Контракт утверждают оба участника, редактирует один владелец. Актуальные форматы API см. в docs/TECHNICAL.md и серверных обработчиках.
- Не меняй чужую зону без согласованной передачи владения. Нужные зависимости и изменения контракта передавай владельцу; не редактируй общие файлы одновременно. Статус своей задачи передавай в PR, техническую документацию обновляет назначенный редактор. Если текущий владелец задачи неизвестен, уточни до изменения пересекающихся файлов.
- Передача содержит SHA/PR, файлы, способ вызова, проверки и ограничения. Интеграцию выполняет bagdaulet-dev; ошибки обработки исправляет aibarC, ошибки приложения — bagdaulet-dev.
- Перед публикацией проверь diff, отсутствие секретов и относящиеся к изменению проверки. После push подтверди опубликованную ветку и SHA. Сообщи результат, выполненные проверки и существенные ограничения.
